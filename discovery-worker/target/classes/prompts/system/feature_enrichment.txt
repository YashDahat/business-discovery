# FEATURE INSTRUCTION RULES

1. HOLISTIC SCOPE
The featureInstruction covers all files in the feature together. It describes how they form a complete vertical slice — persistence, business logic, API surface, and (for FRONTEND features) UI interaction. Do not write separate instructions per file; write one coherent brief from which all files can be derived.

2. EXACT IDENTIFIERS
Every class name, field name, method name, parameter name, and type must appear exactly as defined in the feature's file specs. No synonyms, no abbreviations.

3. COMPLETE METHOD CONTRACTS
For every public method in the feature, specify:
- Exact signature (return type + parameter types and names)
- Logic as numbered steps precise enough to implement without assumptions
- Error cases: what exception is thrown and what HTTP status the controller returns

4. INTER-FILE WIRING
Explicitly describe how the files call each other. Example: "OrderController injects OrderService. OrderService injects OrderRepository and PaymentService (from the payment-processing feature). OrderService.createOrder() calls orderRepository.save() then paymentService.initiatePayment()."

5. CROSS-FEATURE CONTRACTS
Use the peer API summaries to specify exactly which method signatures and endpoint paths this feature calls from other features. Never invent a signature absent from the peer summaries.

FIELD NAMES ARE CONTRACTS TOO: peer summaries include "data_shapes" — the exact field
names and types of each DTO/entity the peer exposes. When this feature's instruction
mentions data another feature owns (e.g. a page rendering membership plans), use the
EXACT field names from data_shapes. Never invent, rename, or add fields — if data_shapes
says durationInMonths, writing durationMonths guarantees a downstream compile failure;
if a field is not listed (e.g. features), it does not exist and must not be referenced.

# PER-FILE STRUCTURAL DETAIL RULES (the "files" array)

## Exactness
Exact identifiers, not descriptions — literal field names/casing ("menuItemId");
concrete types ("UUID", "decimal(10,2)", "List<MenuItem>", never "number"/"object");
endpoints as method + full path + params ("GET /api/v1/menus/{menuId}/items?category={category}");
return AND error types with status codes. Integrating artifacts must match exactly —
if a controller calls getOrderById(UUID): OrderResponse, the service declares it
identically. Trace every cross-reference before finalizing.

## Layer-specific field rules
- MODEL: public_variables = ALL @Column fields with Java type + constraints; api_endpoints = null
- REPOSITORY: public_functions = ALL custom query methods with exact signatures; api_endpoints = null
- SERVICE (backend): public_functions = ALL public methods using Request/Response DTOs (not entities); api_endpoints = null
- CONTROLLER: api_endpoints = FULL endpoint list; public_functions = handler method signatures
- DTO: public_variables = ALL fields with Java type + Bean Validation annotations; api_endpoints = null
- EXCEPTION: minimal public_functions; api_endpoints = null
- PAGE: api_endpoints_consumed = null (pages call hooks, not backend directly)
- COMPONENT: public_functions = component name with props type; api_endpoints = null
- HOOK: public_functions = the hook signature; api_endpoints_consumed = null (hooks call services)
- SERVICE (frontend): api_endpoints_consumed = backend endpoints this service calls; public_functions = all exported async functions

## file_role
Set "file_role" on every file: a short (1–2 sentence) structural description of what
this specific file does within its feature, naming the exact public method signatures
that other features' files will call.
Example: "SERVICE layer — implements createOrder(CreateOrderRequestDTO): OrderResponseDTO and
getOrderById(UUID): OrderResponseDTO; delegates payment to PaymentService and persistence to OrderRepository."

Files under frontend/src/types/ or frontend/src/services/ are DERIVED from the backend
API contract at build time — give them file_role "Generated from the backend API contract —
<one line on the domain>" and skip their public_functions/api_endpoints_consumed detail.

## Outline owns the file list
Emit detail ONLY for the file paths listed in this feature's files. Never add, remove,
or rename files — if the instruction needs a file that doesn't exist, work within the

# SECURITY CONTRACTS (authentication / shared-backend features)

## SecurityConfig authorization model — this exact order, no exceptions:
  .authorizeHttpRequests(auth -> auth
      .requestMatchers("/api/v1/auth/**").permitAll()
      .requestMatchers("/api/v1/<public-endpoints>/**").permitAll()   // menu, public reservations, etc.
      .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
      .requestMatchers("/api/**").authenticated()
      .anyRequest().permitAll()                                       // static files + SPA routes
  )
The LAST rule MUST be anyRequest().permitAll() — NEVER anyRequest().authenticated().
Spring Security intercepts ALL requests including /index.html and /assets/*.js;
authenticated() there blocks the entire frontend.

## ROLE_ authority consistency (mismatch = every admin endpoint 403s)
hasRole("ADMIN") and @PreAuthorize("hasRole('ADMIN')") match the authority "ROLE_ADMIN".
Wherever authorities are built:
    return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));
NEVER new SimpleGrantedAuthority(role.name()). Use hasRole (not hasAuthority)
consistently in SecurityConfig and every @PreAuthorize.

## No circular bean dependency (JwtAuthFilter ↔ UserService ↔ SecurityConfig)
This exact 3-way cycle crashes the app at BOOT (not compile time — the JVM builds fine,
then Spring refuses to start): SecurityConfig constructs JwtAuthFilter as a bean,
JwtAuthFilter's constructor takes UserService, and UserService (or its
AuthenticationManager wiring) ends up needing something SecurityConfig provides.
Break it with EITHER:
  (a) JwtAuthFilter takes UserDetailsService, not the concrete UserService type, injected
      normally — the interface type alone does not remove the cycle if SecurityConfig
      still directly `new`s or wires JwtAuthFilter with a field from itself; OR
  (b) JwtAuthFilter's field for UserService/UserDetailsService is @Lazy:
        public JwtAuthFilter(JwtUtil jwtUtil, @Lazy UserDetailsService userDetailsService)
  AuthenticationManager MUST come from AuthenticationConfiguration.getAuthenticationManager()
  as its own @Bean method in SecurityConfig — never constructed inline inside the
  SecurityFilterChain bean method, and never a parameter SecurityConfig's constructor
  requires from another security bean.
State explicitly in the instruction: "JwtAuthFilter's UserDetailsService (or UserService)
parameter is @Lazy" whenever this feature includes JwtAuthFilter.

## SpaController
@Controller (not @RestController); single method @GetMapping(value = {"/", "/{path:[^\\.]*}"})
returning "forward:/index.html"; no other methods. Never add a `/**` suffix — it would
catch /assets/index.js and defeat the static resource handler.

## JwtUtil
getSigningKey() calls Decoders.BASE64.decode(jwt.secret); uses io.jsonwebtoken (jjwt).
generateToken(UserDetails): String; validateToken(String, UserDetails): boolean;
extractEmail(String): String.

# ADMIN CRUD ZOD CONTRACT (FRONTEND admin features — mismatches cause TS2322 compile errors)
Admin{Domain}Page.tsx uses react-hook-form + zod. The zod schema fields must produce
TypeScript types that exactly match the Create{Domain}Request interface fields:
- Backend @NotBlank String field  → z.string().min(1)    (NOT .optional())
- Backend String price field      → z.string()           (NOT z.number() — sent as string over the wire)
- Backend @Positive/@Min int/BigDecimal field → z.coerce.number()
  (HTML inputs yield strings — plain z.number() makes the resolver type `unknown`)
- Backend Optional/nullable field → z.string().optional() or z.coerce.number().optional()
When building the request object in onSubmit(), types must match the interface directly —
no String() casts or ?? '' patches should be needed if the schema is correct.

When writing featureInstruction for BACKEND features, these rules override training data.
The code generator will follow your instruction literally — if your instruction uses SB2/3

JACKSON — groupId changed. In every instruction that involves JSON parsing:
  Correct imports: tools.jackson.databind.ObjectMapper, tools.jackson.core.JacksonException

REPOSITORY METHODS — name every non-standard method explicitly in the instruction:
  Spring Data JPA does NOT auto-generate undeclared methods. If the service calls

  "UserRepository declares: findByEmail(String email): Optional<User>"
  List all custom finder methods — omitting one causes a guaranteed compile failure.

EXCEPTION CLASSES — never instruct a service to throw an exception that isn't in the manifest:
  ResourceNotFoundException, PaymentGatewayException, etc. must each have a standalone .java

  If unsure, throw IllegalArgumentException or IllegalStateException instead (both are built-in).
