# TASK

# DIAGNOSIS & FIX RULES
1. ROOT CAUSE, NOT SYMPTOM: Identify why the code does not compile, then fix that.
   - Resolve symbol references, import paths, and dependencies against the ACTUAL codebase
     context provided — use the real package paths, class names, and method signatures that
     exist, not plausible-sounding guesses.
   - Common causes to check (Java): missing/incorrect import, wrong package path, misspelled
     or renamed symbol, signature mismatch, missing generic type, unresolved dependency,
     type mismatch, missing override/annotation, visibility, unhandled checked exception.
   - Common causes to check (TypeScript/TSX): wrong or missing import path, unused import
     (noUnusedLocals), type mismatch, missing/wrong generic, incorrect JSX usage, wrong
     module resolution (use relative paths for local files, package names for node_modules),
     TS error codes like TS1434/TS1002 on line 1 mean the file starts with non-TypeScript
     content (e.g. prose or markdown fences) — rewrite the file as pure TypeScript.
   - Do NOT suppress errors by deleting the failing call, stubbing it out, casting blindly,
     swallowing exceptions, or commenting code out unless that is genuinely the correct fix.

2. MINIMAL FOOTPRINT: Change only what is required to resolve the error. Preserve all
   unaffected logic, comments, whitespace, ordering, and formatting exactly. Do not refactor,
   rename, reorder imports, or reformat code unrelated to the fix.

3. USE CONTEXT AS GROUND TRUTH: When resolving a symbol, prefer the definition that exists in
   the provided context over inventing one. If a referenced class/method exists in context
   with a specific signature, match it exactly (e.g. a call to getMenuById(menuId: UUID) must
   use that exact name, parameter type, and return type). Only add a new import if the symbol
   genuinely resolves to that path in the codebase.

4. NO NEW ERRORS: The corrected file must compile cleanly as-is — all imports present and
   resolvable, no dangling references, no newly introduced type errors, and no unused-import
   churn from your change.

5. STANDALONE TYPES — DO NOT INLINE: This project is a pipeline that generates files in
   order. If the error is "cannot find symbol: Foo" and Foo is not present in the context
   files, it means Foo.java will be generated as a separate standalone file. In that case:
   - Keep or add an import statement for the correct fully-qualified name
   - Do NOT declare Foo inline as a nested class, enum, or record
   - Do NOT remove the reference to Foo — the standalone file will exist once the pipeline
     progresses
   If the standalone file's package is unclear from the error, guess .model for entities/enums
   and .dto for request/response classes.

6. SCOPE: Fix only this one file. If the true root cause clearly lies in another file
   (e.g. a method that genuinely doesn't exist anywhere), apply the most correct fix
   possible within THIS file given the contract the context implies, rather than altering
   code you cannot return.

7. SPRING BOOT 4 / JACKSON 3 AWARENESS — check these before anything else for Java files:
   WRONG_IMPORT_PATH starting with com.fasterxml.jackson → replace with tools.jackson:
     com.fasterxml.jackson.databind.ObjectMapper  →  tools.jackson.databind.ObjectMapper
     com.fasterxml.jackson.databind.JsonNode      →  tools.jackson.databind.JsonNode
     com.fasterxml.jackson.annotation.*           →  tools.jackson.annotation.*
     JsonProcessingException                      →  JacksonException (rename in Jackson 3.x)
   Any "package com.fasterxml.jackson does not exist" error is always this cause.

   HALLUCINATED SUB-PACKAGE — "package X does not exist" for a project-internal package:
   The original code may use a sub-package that doesn't exist (e.g. com.foo.service.impl,
   com.foo.repository.custom). Fix the import to match the actual package inferred from the
   file path of the class in the provided context (backend/src/main/java/com/foo/service/Foo.java
   → package com.foo.service, import com.foo.service.Foo).

   UNDECLARED REPOSITORY METHODS — "cannot find symbol: method findByEmail()" etc.:
   Spring Data JPA does not auto-implement methods that aren't declared in the interface.
   The fix is to add the method declaration to the repository interface, OR if you can only
   touch this one file, use findAll().stream().filter() as a temporary workaround and note it.

8. INVALID LUCIDE ICON — HONOR THE // FIXME[invalid-icon] COMMENT: when a file carries a
   `// FIXME[invalid-icon]: 'X' is not exported by lucide-react …` comment above a lucide import,
   the named symbol is a hallucination with no matching export. Replace it (the import AND every
   JSX/value usage) with ONE of the real icons listed in that comment — do NOT invent a different
   icon name, and remove the FIXME comment once fixed. The listed candidates are verified to exist.
