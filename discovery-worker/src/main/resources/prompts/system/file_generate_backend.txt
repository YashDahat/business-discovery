# SPRING BOOT 4 / JACKSON 3 CONSTRAINTS
This project uses Spring Boot 4.x. Several APIs changed from Spring Boot 2/3. Apply these
unconditionally to every Java file.

JACKSON IMPORTS — groupId changed. Never write com.fasterxml.jackson.*:
  tools.jackson.databind.ObjectMapper      (NOT com.fasterxml.jackson.databind.ObjectMapper)
  tools.jackson.databind.JsonNode          (NOT com.fasterxml.jackson.databind.JsonNode)
  tools.jackson.annotation.JsonProperty   (NOT com.fasterxml.jackson.annotation.JsonProperty)
  tools.jackson.core.JacksonException     (NOT JsonProcessingException — it was renamed)
Any import starting with com.fasterxml.jackson is wrong. Replace with tools.jackson.

EXCEPTION CLASSES — Spring Boot 4 ships NO application-level exceptions:
  ResourceNotFoundException, PaymentGatewayException, etc. must be separate .java files
  in the .exception package. Never declare them inline. If you reference one that is not
  in the dependency files, add the correct import (com.{pkg}.exception.ClassName) — the
  standalone file will be generated; do NOT inline it as a nested class.

JPA BIDIRECTIONAL SAVE — set the child's owning-side reference BEFORE saving the parent.
  When a parent owns a @OneToMany(cascade=…) collection whose child holds the @ManyToOne +
  @JoinColumn(nullable=false), populating parent.setChildren(list) and then repo.save(parent)
  inserts every child with a NULL foreign key and the request 500s at runtime. Always set the
  back-reference first, e.g.:
      order.setItems(orderItems);
      orderItems.forEach(i -> i.setOrder(order));   // REQUIRED before the save
      orderRepository.save(order);                  // cascade now writes a valid order_id

ENTITY PRIMARY KEYS = Long IDENTITY — every domain @Entity declares its @Id EXACTLY as:
      @Id
      @GeneratedValue(strategy = GenerationType.IDENTITY)
      private Long id;
  NEVER use UUID for a primary key or ANY id field: no `private UUID id`, no
  GenerationType.UUID, no GenerationType.AUTO, no UUID.randomUUID()/UUID.nameUUIDFromBytes for ids.
  Reference another domain entity by its Long id — a foreign-key field is `private Long <entity>Id;`
  (e.g. orderId, planId, classId), a @PathVariable is `Long id`, and a DTO's id field is `Long id`
  (the entity, its DTO, and the frontend type MUST all agree on the id type). Fenced foundation spine
  is the ONLY exception and is left as-is: User.id is Integer, Payment.id is Long, and the platform
  user is referenced by `Integer userId` (see the CURRENT USER rule below). UUID may appear only for
  an external gateway/correlation token, never for a row's own identity.

JPA SEEDING — never assign an @Id that is @GeneratedValue. In a CommandLineRunner/seeder,
  construct each entity with the no-arg constructor + setters (or a builder) and leave the id
  null so Hibernate generates it. Passing an explicit id (e.g. new Trainer(UUID.randomUUID(), …))
  makes Spring Data see a non-null id, treat the row as detached, and issue an UPDATE (merge) that
  matches zero rows — the seeder crashes at boot with ObjectOptimisticLockingFailureException and
  the app restart-loops. Seed every entity the way its siblings do: no id argument.

CURRENT USER = userId, via @CurrentUser — inject the current user with `@CurrentUser Integer userId`
  (foundation resolver; = User.id, null for a guest). NEVER parse the principal as a UUID (no
  UUID.fromString(...), no nameUUIDFromBytes, no hardcoded id). A domain model references the user by
  an `Integer userId` field (= User.id) set from @CurrentUser — NEVER a UUID, and never email/phone
  stored as the link. For the current user's own rows, filter the repository by `userId` (do not
  expose an id path param). Email/phone are login + lookup keys only: when you must find a user by
  them use UserRepository.findByEmail(...) / findByPhone(...).
