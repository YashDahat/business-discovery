# TYPESCRIPT / REACT 19 CONSTRAINTS (every rule fixes a recurring build breaker)
1. TANSTACK QUERY v5 — SERVER STATE MANAGEMENT (applies to every business domain)
   TanStack Query separates SERVER state (data from an API, cached and synchronised)
   from LOCAL state (UI toggles, form values). Use it for any data that comes from the
   backend: menu items, reservations, orders, trainers, blog posts, gallery images —
   anything fetched via a service function. Never use useState + useEffect to fetch.

   TWO HOOKS, TWO PURPOSES — never mix them:

   useQuery  — READ data (GET requests). Result exposes:
     { data, isLoading, isError, error, isFetching, refetch }
     const { data: menuItems, isLoading } = useQuery({
       queryKey: ['menuItems'],          // cache key — array, unique per query
       queryFn: getAllMenuItems,         // service function from @/services/<domain>Service
     });

   useMutation — WRITE data (POST / PUT / PATCH / DELETE). Result exposes:
     { mutate, mutateAsync, isPending, isError, isSuccess, data, error }
     const { mutate: createItem, isPending } = useMutation({
       mutationFn: createMenuItem,       // service function
       onSuccess: () => queryClient.invalidateQueries({ queryKey: ['menuItems'] }),
     });
     // To trigger: createItem(formData)  or  await mutateAsync(formData)

   COMMON MISTAKES TO AVOID:
   - NEVER call query.queryFn() — queryFn is an internal config, not callable on the result.
   - NEVER use mutation.isLoading — it was renamed to mutation.isPending in v5.
   - NEVER use positional form: useQuery(['key'], fn) — object form only in v5.
   - NEVER use useState + fetch/axios for server data — use useQuery instead.
   - ALWAYS invalidate the relevant queryKey in onSuccess so the UI refreshes.
   - queryKey should match the domain noun: ['menuItems'], ['reservations'], ['orders'],
     ['trainers'], ['blogPosts'], ['galleryImages'] — consistent naming prevents stale cache.
2. EXPLICIT RETURN TYPES ON ALL EXPORTED FUNCTIONS (mandatory — never omit): every exported

     export const formatDate = (iso: string): string => { ... }
     export const useCart = (): CartController => { ... }
   Never rely on TypeScript inference for any exported function. The return type is the cross-file
   contract — downstream files import and call this function based solely on what is declared here.
   Without the annotation the shape is invisible to static extraction and consumers will invent the
   interface. This applies to every exported symbol: hooks, utilities, formatters, context accessors,
   and any other named export that crosses a file boundary.

4. IMPORT FORM — match the export form of the target file exactly (TS2614 otherwise):

   - NEVER write `import { Layout } from './Layout'` when Layout.tsx uses `export default function Layout`.
     This is a compile error (TS2614) every single time — it is not a "maybe".
   - Rule of thumb: page and component files (*.tsx) almost always use `export default`. Utility files
     with multiple exports (hooks, services, types, utils) use named exports.
