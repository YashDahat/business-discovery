## Step 2a — Page composition (MANDATORY — applies to every PAGE from Steps 1–3a)
A Page.tsx is a THIN SHELL: layout, data wiring via its hook, and composition of named
COMPONENT files. Every distinct UI concern inside a page is its OWN component file entry:
a form, a table or grid, a list, a dialog, a card, a hero/summary section. Never plan a
page that implements these inline — a monolithic page is un-updatable (any client change
regenerates the whole file) and routinely exceeds the LLM output budget.

- Path + naming convention (stable identity — a change request must resolve to the same
  file every run): frontend/src/components/<domain>/<Concern>.tsx, named domain-first:
  components/menu/MenuTable.tsx, components/menu/MenuItemForm.tsx,
  components/reservation/ReservationForm.tsx, components/order/OrderSummaryCard.tsx.
- The page lists every one of its components in imports_from; each component is a full
  file entry (layer: COMPONENT) in the files array, in the SAME feature as its page.
- Components receive data and callbacks via PROPS from the page (which owns the hook
  call). Sibling components NEVER import each other; shared shapes live in types/<domain>.ts.
- DECOMPOSITION TRIGGER: any page containing a form, a table, or a dialog MUST be
  decomposed; any page whose description names 3+ sections MUST have one component per
  section. Admin pages (table + create/edit form + delete confirmation) are always
  decomposed — e.g. AdminMenuPage.tsx → components/menu/MenuTable.tsx +
  MenuItemForm.tsx + DeleteMenuItemDialog.tsx.
- Only a trivial static page (a Contact page that is one address block and an embedded
  map) may remain a single file.

Every Java enum and record MUST be its own top-level .java file — never a nested type.

plan the `id` public_variable as type Long, NEVER UUID. Cross-entity reference fields are the

## Singularity principle
Each feature covers exactly ONE business domain and ONE side (backend or frontend). The
same domain on backend and frontend are SEPARATE features.

## Feature type rules
- BACKEND: all Java files for one business domain (model + repo + service + controller + DTOs)
- FRONTEND: all TypeScript/TSX files for one domain (service.ts + Page.tsx +
  AdminPage.tsx + every Step 2a component belonging to those pages; the hook is derived, never planned)
- INFRA: ALL infra files (CI workflows, nginx.conf if any). Exactly one INFRA feature per
  project, named "infrastructure". No enrichment runs for it.
- SHARED: cross-cutting backend utilities — GlobalExceptionHandler, ErrorResponse.
  (The foundation pre-scaffolds: SpaController, User, Role, SecurityConfig, PasswordEncoderConfig,
  JwtUtil, JwtAuthFilter, AuthController, Auth DTOs, UserRepository, UserService, AdminInitializer,
  and the full payment spine. None of these appear in SHARED or any feature — they are closed for
  modification and open for extension: generated code imports/uses them, never reimplements them.)

## Size rule
4–10 files per feature, NOT counting COMPONENT files. If a domain exceeds 10 non-component
files, split into sub-features: e.g. "order-management-core" (entity, repo, service) and
"order-management-api" (controllers, DTOs). A page and its Step 2a components are
INSEPARABLE — they always stay in the same feature (their prop contracts are designed
together in the per-feature pass), so never move components to a sub-feature to satisfy
the count.
