# TASK
Produce a machine-readable project blueprint as a single JSON object. This blueprint is
the AUTHORITATIVE specification — every subsequent code-generation call receives it as its
sole source of truth. Any ambiguity here propagates into broken or inconsistent code
downstream, so precision is the primary success criterion.

# SPECIFICATION RULES
1. EXACTNESS: Specify exact identifiers, never descriptions of them.
   - Field names in their literal casing (e.g. "menuItemId", not "the menu item ID")
   - Parameter types using concrete language-level types (e.g. "string", "int64", "UUID",
     "decimal(10,2)", "List<MenuItem>") — never "number" or "object" when a precise type exists
   - Endpoint paths with HTTP method, full path, and path/query param notation
     (e.g. "GET /api/v1/menus/{menuId}/items?category={category}")
   - Return types and error types for every operation, including status codes

2. CROSS-FILE CONSISTENCY (critical): When two artifacts integrate, their specs MUST match
   exactly — same method signatures, same types, same names on both sides of the boundary.
   - Example: if MenuController calls MenuService.getMenuById(menuId: UUID): MenuItem,
     then MenuService's spec must declare getMenuById(menuId: UUID): MenuItem identically.
   - Before finalizing, trace every cross-artifact reference and verify the producer's
     output type/signature equals the consumer's expected type/signature.

3. COMPLETENESS: Every artifact a downstream call must generate is present with enough
   detail to implement with zero additional assumptions. If a detail is required for
   correct code but unspecified by the input, choose the conventional production default
   and encode it explicitly rather than leaving it open.

4. NO ORPHANS: Every type referenced (as a param, return, or field) must be defined
   somewhere in the blueprint, or be a documented language/library primitive.

# OUTPUT CONTRACT
- Return ONLY the JSON object. No markdown fences, no prose, no preamble, no trailing commentary.
- The output MUST be valid JSON (parseable by a strict parser) and MUST conform exactly to
  the provided schema — every required field present, no extra fields, correct types.
- If the schema is provided in this context, match it field-for-field. Do not invent
  top-level keys.

# SELF-CHECK BEFORE RESPONDING (do not include this in output)
- Is every type referenced also defined or a known primitive?
- Does every integration boundary have matching signatures on both sides?
- Does the output parse as strict JSON with no fences or text around it?
- Does it validate against the schema with no missing/extra fields?
