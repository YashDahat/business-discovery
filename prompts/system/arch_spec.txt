# JAVA TYPE RULES (backend — enforced at generation time)
Every Java enum and record MUST be its own top-level .java file. Never declare an enum
or record as a nested type inside another class.

WRONG:
  // inside Reservation.java
  public enum ReservationStatus { PENDING, CONFIRMED, CANCELLED }

  // inside CreateOrderRequest.java
  public record OrderItemRequest(UUID menuItemId, @Min(1) int quantity) {}

CORRECT:
  ReservationStatus.java → standalone file, layer = MODEL
  Reservation.java → imports com.{slug}.model.ReservationStatus

  OrderItemRequest.java → standalone file, layer = DTO
  CreateOrderRequest.java → imports com.{slug}.dto.OrderItemRequest

This rule applies to every enum and record in the project. If a domain entity needs an
associated status enum, or a request DTO needs a nested item record, each is a SEPARATE
entry in the files array with its own file_name, file_path, and the appropriate layer.
The parent file only references them by import — it never declares them inline.

# SPECIFICATION RULES
1. EXACTNESS: exact identifiers, not descriptions — literal field names/casing
   ("menuItemId"); concrete types ("UUID", "decimal(10,2)", "List<MenuItem>", never
   "number"/"object"); endpoints as method + full path + params
   ("GET /api/v1/menus/{menuId}/items?category={category}"); return AND error types with
   status codes.
2. CONSISTENCY: integrating artifacts must match exactly — same signatures, types, names on
   both sides. e.g. if MenuController calls getMenuById(menuId: UUID): MenuItem, MenuService
   declares it identically. Every frontend service.ts method must match its Controller
   endpoint (path, method, request/response types). Trace every cross-reference before
   finalizing.
3. COMPLETENESS: enough detail to implement with zero assumptions; for any required-but-
   unspecified detail, encode the conventional production default explicitly.
4. NO ORPHANS: every referenced type is defined in the blueprint or is a known primitive.

# DESIGN RICHNESS
The brief contains designDirection, colorScheme, and tone fields describing the intended
visual experience. Use them actively when specifying files:

- Page files: derive the specific sections for that page from designDirection. A bar with
  "full-bleed dark hero + card grid with category filters" means HomePage.tsx has a
  full-bleed hero section, a filterable grid section, and a sticky CTA bar — not a generic
  layout. Name these sections in the file's description field.
- Component files: use colorScheme to specify which Tailwind color classes to use (e.g.
  bg-[#1c1c1e], text-[#f5f0e8], accent via text-[#d4a843]). Put this in the description
  field so the generation LLM uses real colors, not placeholder grays.
- Hook/service files: unaffected by design — derive from the contract only.

# FEATURE GROUPING (required in every output)

Output a "features" array alongside the "files" array. Every file in "files" must appear
in exactly one feature's "file_paths" list, and every file must have "feature_name" and
"file_role" set.

## Singularity principle
Each feature covers exactly ONE business domain and ONE side (backend or frontend). The
same domain on backend and frontend are SEPARATE features.

## Feature type rules
- BACKEND: all Java files for one business domain (model + repo + service + controller + DTOs)
- FRONTEND: all TypeScript/TSX files for one domain (service.ts + hook + Page.tsx + AdminPage.tsx)
- INFRA: ALL infra files (Dockerfile, docker-compose.yml, CI workflows, nginx.conf, .env.example,
  .gitignore). Exactly one INFRA feature per project, named "infrastructure". No enrichment runs for it.
- SHARED: cross-cutting backend utilities used by multiple domains: User, Role, JwtUtil,
  JwtAuthFilter, SecurityConfig, AuthController, its DTOs, UserRepository, UserService,
  AdminInitializer.

## Size rule
4–10 files per feature. If a domain produces more than 10 files, split into sub-features:
e.g. "order-management-core" (entity, repo, service) and "order-management-api" (controllers, DTOs).

## Example feature set for a restaurant with Menu, Reservation, Order, Payment features:
BACKEND:  authentication, menu-management, reservation-system, order-management, payment-processing, admin-crud
FRONTEND: auth-ui, menu-display, reservation-booking, order-flow, payment-checkout, admin-portal
INFRA:    infrastructure
SHARED:   shared-backend

## file_role rule
Set "file_role" on every entry in the "files" array. It is a short (1–2 sentence) structural
description of what this specific file does within its feature, naming the exact public method
signatures that other features' files will call.
Example: "SERVICE layer — implements createOrder(CreateOrderRequestDTO): OrderResponseDTO and
getOrderById(UUID): OrderResponseDTO; delegates payment to PaymentService and persistence to OrderRepository."
