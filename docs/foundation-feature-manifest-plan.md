# Foundation Feature Manifest — OCP Onboarding + Per-Project Pruning (Issue 9)

**Date:** 2026-09-05
**Issue:** #9 — *OCP: auto-onboard new foundation features* (from `frontend-error-analysis-prakash-stores-31c78b9a.md`, task 9)
**Extension:** the `webapp-foundation` project must integrate smoothly into **any** generated project, and features must be **discarded when the project doesn't need them**.

---

## ⚠️ Scope decision (2026-09-06) — PRUNING DEFERRED

**We are NOT physically removing unrequired foundation features for now.** The pipeline depends on
`webapp-foundation` heavily; stripping its files (`FeaturePruneNode`, the DISCARD strip) risks
breaking generation in ways that surface as a *new* class of pipeline failure — a cost that isn't
worth it while the foundation is load-bearing everywhere. Every generated project keeps the **full
foundation** on disk, exactly as today. Carrying unused foundation code (an extra dep or an idle
compose service) is the cheaper, safer state.

**In scope now — the declarative / derive half only:**
- The manifest as a **declaration** of foundation features (§1).
- Deriving the hardcoded seams (`FOUNDATION_CONTROLLERS`, `GUARD_NAMES`, `AUTH_KEYS/NON_NAV_KEYS`,
  fenced symbols) from the manifest instead of hardcoded `Set`s — the OCP *onboarding* half (§5).
- **§6b** — declaring the consumed set in `ARCHITECTURE.json` and referencing it in file
  descriptions + enrichment (planner-asserted, foundation-safe).

**Deferred (future issue) — the pruning half:** `FeatureSelectionNode`'s DISCARD computation (§3),
`FeaturePruneNode` (§4), and the physical file/dep/compose/env strip in §2's flow. The sections
below are kept as the design of record for that future work; treat "kept closure" as "**all**
features" until pruning is actually built. When pruning is picked up it must be gated behind its own
validation so a mis-prune can't reach a generated repo.

---

## The problem in one paragraph

`webapp-foundation` ships **everything** — auth, payments, gallery/media, the app shell, shared
exceptions — and the pipeline hard-codes *what to skip* in three places. A new foundation feature
therefore needs pipeline **code** edits (OCP violation), and every generated project carries the full
foundation whether it needs payments/gallery or not (dead code, unused deps, orphan compose services).

The three hardcoded seams that violate OCP today:

| Seam | Location | Breaks when the foundation adds… |
|---|---|---|
| `FOUNDATION_CONTROLLERS` (SDK skip set) | `util/ApiInventory.java:53` | a new backend controller → not skipped → duplicate/re-plan |
| `GUARD_NAMES = {ProtectedRoute, AdminLayout, siteConfig}` | `util/FoundationRefReconciler.java:84` | a new shell/guard component → not recognized |
| `AUTH_KEYS` / `NON_NAV_KEYS` (route gates) | `util/RouteManifest.java:50,53` | a new gated foundation page → not classified |

---

## The one idea

> **The foundation declares its features in a manifest. The pipeline derives every seam from the
> *kept closure* of that manifest — never from a hardcoded set.**
>
> - Add a feature → append to the manifest. *Open for extension.* (onboarding)
> - A project doesn't need a feature → drop it from the closure. *Same lever, opposite end.* (pruning)

The two `FOUNDATION_CONTRACT.md` cards are **already feature-sectioned** (`## Auth & users`,
`## Payments`, `## Media library + gallery`, `## Shared exceptions`). This makes those sections
machine-declarative so the pipeline can *project* them instead of hard-coding them.

## 1. The manifest — `foundation.manifest.json` (foundation-owned)

Ships at the foundation root, regenerated by the foundation itself (same discipline as the contract
cards). One entry per feature:

```jsonc
{
  "features": [
    {
      "id": "auth",
      "core": true,                          // core → never prunable
      "requires": [],
      "need": { "always": true },
      "backend":  { "controllers": ["AuthController.java"],
                    "packages": ["security", "config/SecurityConfig"],
                    "fenced": ["User","Role","JwtAuthFilter","AuthController", ...] },
      "frontend": { "modules": ["/context/authcontext","/hooks/useauth",
                                "/services/authservice","/types/auth."],
                    "guards":  ["ProtectedRoute","AdminLayout"],
                    "pages":   [{ "key":"LOGIN", "gate":"PUBLIC", "nav":false }] },
      "config":   { "env": ["JWT_SECRET"], "compose": [] }
    },
    {
      "id": "payment",
      "core": false,
      "requires": ["auth"],
      "need": { "signal": "commerce" },      // decided from the brief (see §3)
      "backend":  { "controllers": ["PaymentController.java"],
                    "packages": ["gateway","event"],
                    "fenced": ["Payment","PaymentStatus","PaymentService", ...] },
      "frontend": { "modules": ["/context/checkoutcontext","/src/cart/"],
                    "guards": [],
                    "pages":  [{ "key":"CHECKOUT", "gate":"AUTH", "nav":false }] },
      "config":   { "env": ["RAZORPAY_KEY_ID","RAZORPAY_KEY_SECRET"], "compose": [] }
    },
    {
      "id": "gallery",
      "core": false,
      "requires": ["auth","storage"],
      "need": { "signal": "media_gallery" },
      "backend":  { "controllers": ["GalleryController.java","AdminMediaController.java"],
                    "packages": ["storage"], "fenced": ["MediaAsset", ...] },
      "frontend": { "modules": ["/components/gallery/","/hooks/usemedia"],
                    "guards": [], "pages": [{ "key":"GALLERY", "gate":"PUBLIC", "nav":true }] },
      "config":   { "env": ["S3_ENDPOINT","S3_BUCKET","S3_PATH_STYLE"], "compose": ["minio"] }
    }
  ]
}
```

The three hardcoded sets become **projections of the kept closure**:

```
FOUNDATION_CONTROLLERS = ⋃ kept.backend.controllers
GUARD_NAMES            = ⋃ kept.frontend.guards
AUTH_KEYS/NON_NAV_KEYS = from kept.frontend.pages[].gate / .nav
env / compose to keep  = ⋃ kept.config.*
FoundationSymbolRegistry fences = ⋃ kept.*.fenced   (kept features only)
```

**Graceful degradation** (the existing `FoundationSymbolRegistry` pattern): if the manifest is absent,
fall back to parsing the `##` sections of the two contract cards + a directory scan, so a foundation
clone predating this feature still works and downstream reconciliation no-ops.

## 3. Selection — the PLANNER decides; the mechanics only GUARD

> **⚠️ DEFERRED — pruning half.** Design-of-record only; not built now. See
> [Scope decision (2026-09-06)](#️-scope-decision-2026-09-06--pruning-deferred). Until pruning is
> built, there is no DISCARD set — every feature is kept, and the guardrails below are unnecessary.

**The decision is the planner's, not a mechanical classifier's.** The planner already reads the whole
brief (`mustHaveFeatures`, `niceToHaveFeatures`, `recommendedPages`, `websiteType`,
`businessCategory`, competitor/industry insights) and is *already* deciding the business's domain
features — deciding "this business needs payments" is the same judgment on the same inputs it uses to
plan the order/checkout flow. So the kept set of foundation features is emitted **by the planner as it
generates `ARCHITECTURE.json`** (the `foundation_features` assertion of §6b Part A). We do NOT run a
separate keyword/Flash classifier that competes with the planner — one actor, one decision, same
inputs. A second decider only risks the two disagreeing (classifier keeps `gallery` but the planner
never plans a gallery page, or the reverse).

**Why not a mechanical selector at all?** Because splitting the choice out duplicates reasoning the
planner already does and creates drift between a keyword list and the prompt. The planner is
best-positioned; let it decide.

**Where mechanics DO earn their place — as guardrails around a destructive prune, never as the
decider.** Pruning (§4) physically `rm`s code, so a wrong *keep/drop* call deletes needed code and
breaks the build. Two cheap, deterministic nets wrap the planner's decision. Neither ever overrides a
KEEP — they only *add back* what safety requires:

```
kept ← planner.foundation_features           # THE DECISION — the planner's assertion (§6b Part A)
kept ← kept ∪ { f : f.core == true }          # GUARD 1: core is non-negotiable, always kept
kept ← transitiveClosure(kept, requires)      # GUARD 2: pull in dependencies the decision implies
                                              #          (checkout ⇒ cart+payment; gallery ⇒ storage)
discard ← allFeatures − kept                  # only what survives BOTH guards may be pruned
```

- **Guard 1 — core floor.** `core` features (auth, shell, exceptions) are kept regardless of what the
  planner said; they are structural, not business-optional.
- **Guard 2 — `requires` closure.** A hard dependency-graph guarantee, not a judgment: if payment is
  kept, auth comes too; if gallery, then storage. Prevents a kept feature from dangling on a
  dropped dependency.
- **Guard 3 — reference veto (runs after planning/reconcile).** If any *planned domain model* still
  carries a fenced handle of a would-be-`discard` feature (e.g. a `Payment referenceId`, the exact
  handle `FoundationRefReconciler` rewrites), the prune is **vetoed** and that feature is force-kept.
  This guarantees the planner's decision can never produce a dangling reference.

The brief fields feeding the planner's decision live on `ArchitectBrief`
(`worker/model/ArchitectBrief.java:56-64`).

## 4. The pruning algorithm (`FeaturePruneNode`) — safe removal on four surfaces

> **⚠️ DEFERRED — pruning half.** This entire section is design-of-record; `FeaturePruneNode` is
> **not built now** and nothing physically `rm`s foundation code. See
> [Scope decision (2026-09-06)](#️-scope-decision-2026-09-06--pruning-deferred).

A feature touches four surfaces; **all four must go together** or the build breaks.

| Surface | What prune does | Why it stays consistent |
|---|---|---|
| **Workspace files** | physically `rm` the feature's backend packages/controllers + frontend modules/pages from the cloned foundation, *before generation* | the shipped repo simply never contains the code |
| **Seam-sets** | *nothing explicit* — the sets are derived from the **kept** closure, so a pruned feature is absent by construction | no set can name a feature that isn't in `kept` |
| **Config / infra** | drop the feature's `env` keys (feeds `EnvVarScanner` typed-defaults) + `compose` services (e.g. `minio`) + Dockerfile bits | no orphan env var, no dead compose service |
| **Generator input** | after the planner has decided the kept set and DISCARD code is stripped, the generators re-read the workspace and see **only kept-feature code** | a generator can't import or re-build a capability whose files were removed |

## 5. Wiring — worker pipeline order

> **⚠️ Partly DEFERRED.** Loading the manifest, the **planner's `foundation_features` decision**, and
> deriving the seams from the manifest are the **in-scope onboarding half**. The guardrails +
> `FeaturePruneNode` are the deferred pruning half (see
> [Scope decision (2026-09-06)](#️-scope-decision-2026-09-06--pruning-deferred)); read "KEPT" as "the
> **full** manifest (all features)" until pruning lands.

The foundation is cloned **inside `ProjectPlanningNode`** (`ProjectPlanningNode.java:143-155`), right
before it plans — so the manifest is loaded at the same point the fenced-symbol registry is already
built (`:160-161`), not in a separate pre-planning node. The planner then emits `foundation_features`
as it writes `ARCHITECTURE.json`.

```
ProjectPlanningNode
  ├─ cloneFoundation → /workspace                              (existing, :143-155)
  ├─ load FoundationManifest (all features)   (NEW, IN SCOPE)  inline at :160-161, beside
  │                                                            FoundationSymbolRegistry.buildFromWorkspace
  ├─ PLANNER decides: emits foundation_features = kept set     (NEW, IN SCOPE, §6b Part A)
  ├─ GUARDRAILS: core floor + requires-closure + ref-veto      (DEFERRED)  validate KEPT/DISCARD
  ├─ FeaturePruneNode: strip DISCARD files/deps/compose/env    (DEFERRED)  emit docs/FEATURES.json
  └─ derive seams from KEPT  (FoundationSymbolRegistry + FOUNDATION_CONTROLLERS + GUARD_NAMES + …)
                                                               ← IN SCOPE (all features today)
  → FileManifestGeneratorNode → ProjectScaffoldNode → … (unchanged)
```

Code changes to land the OCP (onboarding) half — **in scope now**:
- **Delete** the three hardcoded `Set`s (`ApiInventory.FOUNDATION_CONTROLLERS`,
  `FoundationRefReconciler.GUARD_NAMES`, `RouteManifest.AUTH_KEYS/NON_NAV_KEYS`).
- Each reads from the `FoundationManifest` instead (all features, since nothing is pruned).
- `FoundationSymbolRegistry.buildFromWorkspace` fences symbols from the manifest.

## 6. Why it's correct — the invariant

> **⚠️ Invariants 1–4 assume pruning.** Pruning is **deferred** (see
> [Scope decision (2026-09-06)](#️-scope-decision-2026-09-06--pruning-deferred)), so with the full
> foundation kept there is no DISCARD set and nothing to dangle to — these hold trivially today.
> They become load-bearing only when the pruning half is built.

1. **Closed-world planner** — the planner sees exactly the kept features, so it can't reference a
   pruned symbol; there is nothing to dangle to.
2. **Derive-from-kept** — every seam (controllers / guards / gates / env / compose / fenced symbols) is
   a projection of the kept closure, so no set survives that names a pruned feature.
3. **Closure + reference veto** — you never prune something a kept feature *or a planned domain model*
   actually needs.
4. **Physical strip before generation** — the shipped repo contains only kept-feature code: no dead
   imports, no unused deps, no orphan compose service → the build stays green. *(Deferred: today the
   full foundation ships, so unused deps/compose services are tolerated per the scope decision.)*

Onboarding (append to manifest) and pruning (drop from closure) are the **same operation** — filter the
manifest, then derive everything from the filtered manifest. That is the OCP the pipeline should hold.
*(For now the filter is the identity — all features kept.)*

## 6b. Declaring the kept set IN `ARCHITECTURE.json` (planner-visible, file-referenced)

§1–§6 make the kept closure a thing the *pipeline* computes. But `ARCHITECTURE.json`
(`ArchitectureSpec`) currently has **no field** recording which foundation features a project
actually consumes — the knowledge lives only as prose in two prompts:

- `arch_outline.txt` — the "PRE-SCAFFOLDED, DO NOT PLAN" blocks (auth spine, payment spine, cart
  framework, media/gallery, shell).
- `feature_enrichment.txt` — the same facts repeated (rules 4, 4b, 9, 10).

So the planner is *told* "these exist," but nothing it emits states "this project uses payment +
auth, not gallery," and no generated `FileSpec.description` records that it imports the fenced
`PaymentService`. The closed-world invariant (§6) is closed only **in the prompt**, never **in the
artifact** — enrichment re-derives the coupling from prose on every feature, with no cross-file
record and nothing for the reconcilers to check against.

### Current state — how `ARCHITECTURE.json` refers to foundation today

There is **no structured foundation reference** in the artifact. A foundation feature shows up only
**implicitly, as free-form strings** on a `FileSpec`:

| Field | How foundation appears | Example |
|---|---|---|
| `importsFrom` | a file may list a fenced path/symbol — `arch_outline.txt` permits *"You MAY list these in another file's imports_from — they exist on disk"* | `["@/hooks/useAuth", "@/cart", "com.slug.service.PaymentService"]` |
| `dependsOn` | the same, at the dependency-wiring level | `["PaymentService"]` |
| `description` / `fileRole` | prose names the handle | *"OrderService injects the pre-scaffolded `PaymentService`…"* |

There is **no** top-level `foundation_features`, **no** per-feature `consumes_foundation`, and **no**
per-`FileSpec` flag distinguishing *"this import is a fenced foundation symbol"* from a sibling
generated file. The consequence: **`ARCHITECTURE.json` alone cannot tell a foundation import from a
domain import** — that distinction is reconstructed *downstream* by name-matching those strings
against `FoundationSymbolRegistry.isFenced(name)` (e.g. in `FoundationRefReconciler`). The
"this-is-foundation" knowledge is not in the artifact; it is inferred from the registry every time.

**Before → after (what §6b changes):**
- *Before:* foundation referenced as ordinary import/dependency strings + prose; foundation-ness
  inferred downstream from the registry.
- *After:* an explicit, machine-readable `foundation_features` declaration (Part A) + a
  `consumes_foundation` edge per feature (Part B), so the artifact itself records the coupling and
  the reconciler can *check* it instead of *infer* it. (Part C — the generator wayfinding rule,
  already shipped — leans on this being explicit.)

### This section

This section makes the kept set a **first-class artifact field**, referenced everywhere a file is
described. It is the structural twin of §1–§6: the manifest/selection nodes decide the kept set;
this records it in the plan and threads it into file descriptions + enrichment.

> **Backend coverage — this is not frontend-only.** The prose examples below lean frontend-heavy
> (`useCart`, `@/shell`, guards get more ink), but every mechanism applies equally to backend
> generation:
> - **Manifest / seams (§1):** each feature has a `backend` block; the derived seams include the
>   backend `FOUNDATION_CONTROLLERS` (`ApiInventory`) and the **BACKEND**-layer symbols in
>   `FoundationSymbolRegistry` (auth/user/payment/exception spine).
> - **Part A:** `consumed_via` carries backend handles (`@CurrentUser Integer userId`,
>   `PaymentService.createOrder`, `PaymentCapturedEvent`).
> - **Part B:** `FeatureCard.consumes_foundation` is set on backend features too
>   (e.g. `order-management` → `["payment","auth"]`).
> - **Part C (shipped):** the `FOUNDATION LOOKUP` clause landed in **both** generator prompts —
>   `file_generate_backend.txt` names the auth/user + payment spine, media/gallery, and shared
>   exceptions.

### Part A — declare the kept set in the outline output

Add a top-level array the outline LLM emits, and a matching field on `ArchitectureSpec`:

```jsonc
"foundation_features": [
  { "id": "auth",    "consumed_via": ["useAuth()", "@/api/client", "@CurrentUser Integer userId"] },
  { "id": "payment", "consumed_via": ["PaymentService.createOrder", "PaymentCapturedEvent"] },
  { "id": "cart",    "consumed_via": ["useCart()", "useCheckout()"] }
  // gallery, storage, … OMITTED because this project doesn't need them
]
```

This is the *kept closure* of §1, stated **by the planner as output** rather than derived by a new
node — so it works **today**, before `FoundationManifestNode`/`FeatureSelectionNode` exist. Model
change: a `FoundationFeatureRef` type (`id` + `consumed_via`) and
`List<FoundationFeatureRef> foundationFeatures` on `ArchitectureSpec` (null on old specs, safe via
`@JsonIgnoreProperties`).

### Part B — reference the kept set where files are described

Two touch points, both converting scattered prose into a machine-readable edge:

1. **File descriptions (outline rule 3 / `FileSpec`).** New OUTLINE RULE: *"If a file consumes a
   `foundation_features` entry, its description must name the capability by its fixed handle
   (`useCart()`, `PaymentService`, `@CurrentUser`) and that handle must appear in `imports_from`.
   Never re-describe the foundation's internals."*

2. **Feature enrichment (`feature_enrichment.txt` + `FeatureCard`).** Feed the kept
   `foundation_features` list into every enrichment call as declared context, and have enrichment
   set a `consumes_foundation: ["payment","auth"]` field on the `FeatureCard`. This gives each
   feature the same machine-readable treatment `depends_on_features` already got for cross-feature
   bean cycles — replacing the per-feature prose of rules 4/4b/9/10 with a checkable edge.

### Part C — generator wayfinding (✅ SHIPPED 2026-09-06)

The last mile: at generation time, when the LLM references a foundation capability it must know
*where to look* for its exact shape/handle. The **FENCED FOUNDATION CONTRACT** block is already
injected into every generation call (`FoundationContractCard` as `sharedContext`), but the "ground
truth" rule didn't name it as a lookup source. **Now added** — a `FOUNDATION LOOKUP` clause in
rule 5 of both `file_generate_backend.txt` and `file_generate_frontend.txt`:

> whenever you reference a fenced FOUNDATION capability (backend: `User` / `@CurrentUser Integer

### Why this shape

- **OCP invariant made auditable** — the kept set is declared once; the file layer and the
  enrichment layer *project from it* instead of each re-deriving from prose.
- **Reconciler target** — `FoundationRefReconciler` can cross-check the invariant
  *"file imports a fenced symbol ⟺ that feature is in `foundation_features`"* — a dangling reference

### Sequencing

`foundation_features` is the **planner's assertion** of what this project consumes — it stands on
its own and needs nothing else in this plan. It is also forward-compatible: if a manifest-driven
selection step is added later, that step computes the kept set and the planner's array becomes a
*validated echo* (a mismatch is a defect the reconciler flags) rather than the source of truth.
